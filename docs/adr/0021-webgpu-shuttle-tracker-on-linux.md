# The shuttle tracker runs on WebGPU on Linux; the other models stay on CPU there

The teacher segmenter (ADR 0019) is 6–7× faster than real time on a GPU and about 1.4× *slower* than real time on CPU, almost all of it TrackNet. On Linux the app's GPU path was ONNX Runtime's CUDA provider, which needs CUDA 12 and cuDNN 9 beside the app: about 1 GB to bundle, and an install most users don't have (current distributions ship CUDA 13). Without them every model silently ran on CPU.

**Linux uses ONNX Runtime's WebGPU provider (Dawn over the system's Vulkan driver) for the shuttle tracker** — TrackNet and InpaintNet. Any Vulkan GPU works with the stock driver, and the download grows by one 13 MB library, `libwebgpu_dawn.so`, shipped beside the binary (deb/rpm `/usr/lib/Voloph`, AppImage `usr/lib`, found via the binary's rpath). Measured on an RTX 3080 over a 10-minute recording: 137 s (4.4× real time, against CUDA's ~7× and CPU's 0.7×), and a shuttle track matching CUDA's on 99.92 % of frames — the same agreement CPU has with CUDA. (Since then the tracker computes each chunk's background from a second, streaming decode instead of holding the chunk's frames, and runs one window per call on CPU: the whole teacher peaks under 1 GB on either provider, down from 2.3 GB on WebGPU and 4.4 GB on CPU, for ~10 % more wall-clock on the GPU.)

**WebGPU is used only where it is checked.** ONNX Runtime 1.22's WebGPU provider computes a convolution with 27 input channels wrongly (TrackNet's first layer: off by up to 0.27 on the output heatmap, 10 % of frames' shuttle positions wrong) without any error. TrackNet's export now widens that convolution to 28 input channels behind an in-graph zero `Pad` (identical sums; < 1e-6 from the old export on CPU). Beyond that one bug, the tracker runs both networks once per process on a fixed input on the GPU and on CPU, and uses CPU if they disagree (`tracknet::ShuttleTracker::load`). The person detector and pose model are not checked, so on Linux they stay on CPU — at the rates the app runs them they are cheap. Windows keeps DirectML for every model (ADR 0015).

Two ONNX Runtime behaviours the integration works around (`src/gpu.rs`):
- **Environment first.** A provider registered before ONNX Runtime's environment exists cannot reach its default logger; WebGPU then fails to register and that session runs on CPU, silently. Every session builder creates the environment first.
- **Exit.** After WebGPU was used, ONNX Runtime's static teardown at process exit destroys cached GPU pipelines after their device and segfaults. The app and the dev CLIs end through `gpu::exit`: with no ONNX session alive it releases the environment first, which runs that cleanup in order; with one alive (quitting mid-analysis) it skips static destructors with `_exit`.

Rejected: **bundling CUDA 12 + cuDNN** — ~1 GB on every Linux download for the subset of users with an NVIDIA GPU; **downloading CUDA on demand** — the same gigabyte, plus a download flow to build and maintain; **using the system's CUDA** — ONNX Runtime 1.22's CUDA build needs CUDA 12 exactly, which rolling distributions no longer ship; **WebGPU for every model** — unverified models on a provider that has already returned wrong answers silently.
